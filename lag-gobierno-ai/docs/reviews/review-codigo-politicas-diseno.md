> Alcance: Todo el código en `src/`, `tailwind.config.ts`, `globals.css`, `prisma/schema.prisma`

## Hallazgos

- **La estructura de archivos contradice `standards.md`.** El estándar define `src/components/[Nombre].tsx` para componentes y `src/lib/validations/[recurso].ts` para validaciones. La implementación usa `src/presentation/components/` y `src/presentation/validations/`. Si bien el design.md adoptó Clean Architecture con 4 capas, `standards.md` (fuente de verdad del proyecto) no fue actualizado para reflejar esta decisión. Hay un conflicto formal entre docs que debe resolverse: o se actualiza `standards.md` para oficializar la estructura Clean Architecture, o se mueve todo a las rutas definidas en el estándar.

- **`src/app/page.tsx` es el boilerplate completo de `create-next-app` sin modificar.** Contiene logos de Next.js/Vercel, links a la documentación de Vercel, clases `dark:invert`, `dark:bg-white/[.06]`, fuentes Geist Mono, y texto en inglés. Es una página muerta que no cumple ningún estándar del proyecto y debería ser una redirección a `/catalogo` o una landing page con branding LAG.

- **`layout.tsx` carga fuentes Geist (GeistVF.woff, GeistMonoVF.woff)** en lugar de Inter como define `design-system.md`. La variable CSS `--font-geist-sans` se aplica al body. La tipografía de toda la aplicación es incorrecta. Además `CatalogoLayout` dice en su JSDoc "Usa font Inter via la clase del root layout" — lo cual es falso.

- **`layout.tsx` declara `lang="en"` en `<html>`.** La aplicación es en español, todos los textos visibles están en español, y el atributo debe ser `lang="es"`. Esto afecta directamente accesibilidad (WCAG AA exige idioma correcto para lectores de pantalla).

- **`layout.tsx` metadata dice `title: "Create Next App"` y `description: "Generated by create next app"`.** Metadata genérica que no fue personalizada. Debería ser "Gobierno AI — Logiztik Alliance Group" o similar.

- **`globals.css` define `--foreground: #171717`** pero el design system establece `text-primary: #383838`. El color base de texto del body no corresponde al estándar aprobado.

- **`globals.css` incluye un bloque `@media (prefers-color-scheme: dark)`** con variables oscuras. El design system dice explícitamente "El tema es LIGHT (claro)". No debe existir soporte para dark mode.

- **`globals.css` define `font-family: Arial, Helvetica, sans-serif`** para el body. Tampoco es Inter. Hay tres fuentes distintas compitiendo: Geist (en layout.tsx), Arial (en globals.css), y la que debería ser (Inter, design-system.md). Ninguna de las dos implementadas es correcta.

- **`tailwind.config.ts` no centraliza los tokens del design system.** Solo define `background` y `foreground` como custom properties. Los 7 tokens de marca + 3 del semáforo deberían estar aquí. Cada componente repite hexadecimales en crudo (`#86B81C`, `#383838`, `#6B7280`, `#E2E8E0`, `#5C8314`, `#DC2626`). Cambiar un color de marca requiere editar 8+ archivos.

- **No existe `vitest.config.ts`.** El `package.json` define `"test": "vitest run"` pero no hay configuración de Vitest ni archivos de test en `src/`. El estándar dice "Tests Unit: Vitest". No hay un solo test unitario en el proyecto. El design.md describe una arquitectura que "habilita tests unitarios sin BD" con Domain puro y repository pattern, pero esa promesa no se cumple.

- **No existe `src/app/catalogo/[id]/loading.tsx`.** El design.md define la jerarquía de rutas con loading.tsx tanto para `/catalogo` como para `/catalogo/[id]`. Solo existe el primero. La página de detalle no tiene skeleton de carga.

- **No se implementó `classifyPrismaError` ni el campo `retryable` en las responses de error.** El design.md sección 5 define una clasificación de errores (Transient/Permanente/Configuración) con lógica de `classifyPrismaError()`. La implementación actual siempre retorna `{ error: "Error interno del servidor" }` sin distinción. `ErrorState` siempre muestra el botón "Reintentar" incluso para errores permanentes — contradiciendo la regla del design: "El botón Reintentar solo se muestra cuando el error es de categoría Transient."

- **No existe `src/domain/herramienta/value-objects/dpa-estado.vo.ts`.** El design.md sección 4 lo define explícitamente: `export type DpaEstado = "Vigente" | "No aplica" | "Pendiente"`. Sin este value object, el campo `dpa` en la entity es un `string` sin tipar — el dominio no puede validar que sus valores son correctos.

- **El schema de Prisma no tiene campo `retiradaEn`.** El design.md sección 3 define `retiradaEn DateTime?` como parte del modelo y la tabla H6 lo lista para herramientas retiradas. La implementación actual muestra un string hardcodeado "Fecha no registrada" en `ToolDetailPage` sin que exista el campo en BD ni en la entity. El campo debe existir incluso si su valor es null en MVP.

- **La validación Zod (`ListHerramientasQuerySchema`) no incluye `categoria` como filtro opcional.** El design.md sección 4 define `categoria: z.string().min(1).max(100).optional()` como parámetro preparado para post-MVP. Este omisión significa que la interfaz `HerramientaFilters` del dominio tampoco lo tiene, cuando el design explícitamente dice "H2: Preparado para Post-MVP (US-07). MVP no lo usa en FilterBar."

- **`BackButton.tsx` invierte la jerarquía hover/base de colores.** Usa `text-[#5C8314]` (brand-dark, definido como "Hover/pressed") como color base y `hover:text-[#86B81C]` (brand-primary) como hover. Según el design system, la lógica correcta es: estado normal = brand-primary (`#86B81C`), hover/pressed = brand-dark (`#5C8314`).

- **`NivelBadge.tsx` introduce colores no autorizados**: `bg-blue-50`, `text-blue-700` (nivel Interna), `bg-amber-50`, `text-amber-700` (nivel Confidencial), `bg-gray-100`, `text-gray-500` (Sin clasificar). Ninguno está en la paleta aprobada del design system. Si se necesitan, deben documentarse en `design-system.md` primero.

- **`SemaforoIndicator.tsx` es inconsistente entre estados.** "Activa" usa `bg-[#86B81C]/10` (token explícito con opacidad), pero "Condicional" usa `bg-amber-50` (clase genérica de Tailwind). El patrón debería ser uniforme: `bg-[#F59E0B]/10` para consistencia.

- **`ToolCard.tsx` usa `text-[#E2E8E0]` para el separador "·".** El token `#E2E8E0` está definido como color de `border` (bordes/separadores). Usar un color de borde como color de texto produce un contraste de ~1.5:1 contra fondo blanco — incumple WCAG AA.

- **El container (`infrastructure/container.ts`) instancia singletons a nivel de módulo sin abstracción de DI.** No hay forma de inyectar un repositorio mock para tests sin hacer monkey-patching. El design.md describe dependency injection pero la implementación la hace irremovible para testing. Debería exportar una factory o usar un container de DI que permita override en tests.

## Nota para el agente dev

Este reporte es complementario a `docs/reviews/review-colores-design-system.md` que cubre específicamente colores. Este documento amplía la revisión a **estructura de código, arquitectura, error handling, campos faltantes, testing, y cumplimiento con el design.md aprobado**.

Antes de implementar correcciones, se recomienda:
1. Resolver el conflicto entre `standards.md` y la estructura Clean Architecture (item 1) para no mover archivos innecesariamente.
2. Centralizar tokens en `tailwind.config.ts` primero (item 5) para que las correcciones de colores se hagan una sola vez.
3. Los items de `retryable` y `classifyPrismaError` (8, 9) requieren decisión: ¿implementar ahora como indica el design, o deferir a post-MVP marcándolo como excepción aceptada?
